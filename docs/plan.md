# План реализации Beat Volumetric

Статус: реализован каркас PR 01; DSP левелера начинается с PR 02. Основа —
[исходная идея](../drum-leveler-project.md). Этот документ задаёт порядок работ
и уточняет её технические допущения. Критерии незавершённых этапов — требования
к будущей реализации. Проведённые проверки записаны в [status.md](status.md).

## Результат и границы релиза

Плагин уменьшает случайный разброс уровня ударов на одной дорожке, сохраняя
акценты, гост-ноты и атаку. Первая версия должна быть полезна на близких микрофонах
бочки, снейра и томов; комната и перкуссия входят в проверку и набор пресетов,
но не дают права обещать одинаковое качество на любом материале.

**1.0:** детекция и отсев просачивания, peak/RMS/weighted измерение, авто/ручная
цель, раздельная сила вверх/вниз, гост-зона, пределы gain, окно применения,
sidechain veto, Dry/Wet, difference, визуализация и измеренные метрики, пресеты,
MIDI out в поддерживающих его хостах.

**Форматы и стенд:** сначала macOS VST3 в Reaper; затем AU в Logic и VST3
в Ableton Live. Standalone — диагностический стенд. CLAP через адаптер — отдельный
неблокирующий шаг после VST3/AU. Windows включается после стабильного macOS-релиза.
Конкретные версии ОС, архитектуры и хостов фиксируются в протоколе беты.
Pro Tools не входит в матрицу 1.0: AAX пока не запланирован.

**1.1:** связывание микрофонов между инстансами. **Позже:** спектрально-избирательное
усиление как отдельное исследование. ARA, редактирование отдельных ударов, замена
сэмплами, фазовое выравнивание и редактор многодорожечной сессии вне этого продукта.

## Связь с основным проектом

Проверено по локальному `../beat-equalizer` при оформлении репозитория:

- C++20, CMake ≥ 3.22, JUCE 8.0.15 и Catch2 v3.8.1; зависимости через FetchContent.
  Это отправная точка для совместимости, не утверждение о последних версиях.
- `src/dsp/OnsetAnalysis.{h,cpp}` считает спектральный поток и полосовые признаки.
  `run()` возвращает динамические массивы, сбрасывает спектральную историю при
  вызове и анализирует готовый блок/файл. Это референс, а не готовый realtime API.
- `docs/detector-design-recommendations.md` задаёт сменный детектор, события,
  уверенность и происхождение. Его двухпроходная калибровка по полной записи
  требует причинной адаптации для потокового левелера.

Переиспользовать признаки, математические примитивы, семантику события и тестовые
подходы. Не переносить `beat_doc`, редактор, GCC-PHAT, N-in/N-out маршрутизацию
или запрет любого анализа в callback из статического выравнивателя.

В PR 02 описать общий контракт событий и потоковую обработку. До переноса кода
зафиксировать источник/commit и способ обновления. Предпочтительный результат —
небольшой общий DSP-модуль с зафиксированной версией и отдельными адаптерами для
файлового редактора и realtime. Выделение модуля в основном репозитории — отдельная
согласованная задача; этот checkout должен собираться самостоятельно. Временный
локальный прототип явно помечается и получает план сведения с общим модулем.

## Архитектура

```text
main input ──┬── delay line ── gain scheduler ── Dry/Wet / difference ── output
             │                         ↑                ↑
             │                         │          delayed dry
             └── streaming detector ── level meter ── gain law
sidechain ────── veto features ──────────┘

DSP telemetry ── bounded queue ── waveform / hit markers / meters
```

| Блок | Ответственность |
|---|---|
| Streaming detector | Признаки, кандидаты, подтверждение, veto, confidence |
| Hit level meter | Окно от начала события; пик, RMS, взвешенная энергия |
| Target tracker | Статистика предыдущих уверенных ударов и адаптивная цель |
| Gain law | Strength, гост-зона, пределы подъёма/ослабления |
| Gain scheduler | Переход до атаки, плато, возврат к единице, плотные пассажи |
| Delay / mixer | Единая latency для wet/dry/bypass и stereo |
| JUCE adapter | Шины, host transport, APVTS, сериализация, MIDI, UI |

Будущее дерево: `src/dsp`, `src/plugin`, `tests`, `tools`, `cmake`, `scripts`,
`docs`. DSP-тесты не поднимают GUI. Файловый стенд подаёт запись кусками через
тот же потоковый движок, которым пользуется плагин, и сохраняет CSV/JSON отчёты.

Минимальная модель: `OnsetEvent` (ID, epoch, onset sample, decision-ready sample,
confidence, provenance), `HitMeasurement`, `GainEvent` (ID удара, gain dB,
границы перехода/плато/возврата). Формат уточняется в PR 02; это ещё не API.
Все времена — в отсчётах входного потока, с независимостью от границ host-блока.
Для 1.1 нужны общая временная шкала и отделённый источник `GainEvent`; скрытые
пользовательские параметры групп и транспорт обмена в 1.0 не нужны.

## Технические уточнения идеи

### Причинность и latency

20 мс lookahead и измерение 50 мс после атаки одновременно невозможны без
дополнительной задержки. Поиск минимума до атаки тоже требует запаса: этот участок
не должен успеть выйти из delay line до готовности коэффициента.

Для прототипа использовать бюджет `L ≥ max(D, W) + P`, где D — наихудшее время
подтверждения онсета относительно его начала, W — горизонт данных измерителя,
P — запас до атаки под размещение перехода. Формула предполагает, что измеритель
может прочитать сохранённые входные сэмплы с момента онсета. Если реализация
последовательная или добавляет кадровое ожидание, его тоже включить в бюджет.
Округления и самый неудачный фазовый сдвиг относительно hop проверяются тестом.

PR 02 должен выбрать: ограничивать W при выбранном L либо увеличивать L и честно
сообщать итог хосту. Диапазон 5–50 мс и default 20 мс из идеи остаются гипотезой
до измерений. Нельзя молча усекать окно или использовать неполный уровень как полный.
Latency-параметры в 1.0 не автоматизируются во время playback; путь изменения
при остановке/переподготовке проверяется по каждому хосту.

### Огибающая и переходы

Постоянный gain сохраняет форму сигнала только на своём плато. Возврат к единице
меняет хвост; при перекрытии ударов на одной дорожке нельзя независимо усилить
каждый из них. В документации и UI это ограничение должно быть видно.

Кроссфейд двух синхронных копий — `x * ((1-a)*g1 + a*g2)`: обычная плавная
смена gain. Он устраняет скачок коэффициента при непрерывном a, но не гарантирует
неслышимость изменения хвоста. Для этих коррелированных копий начать с линейных
весов, сумма которых равна единице. Сравнить с прямой интерполяцией gain.

Планировщик ищет доступный минимум перед атакой в пределах буфера. При отсутствии
паузы ограничивает разницу gain соседних ударов и ослабляет воздействие. Следующий
удар перепланирует возврат, а не умножает независимые окна. Решение, которое
опоздало, не меняет уже начавшуюся защищённую атаку; считать такие случаи отдельно.

### Потоковый анализ и надёжность

Основной путь — ограниченный потоковый DSP без worker, необходимого для срока
готовности gain. FFT, медианы и накопители используют заранее выделенную память;
их стоимость измеряется на малом блоке. Кадры привязаны к счётчику сэмплов.
Если этот путь не укладывается в CPU-бюджет, сначала пересмотреть алгоритм/latency;
переход на worker требует отдельного решения о дедлайнах и поведении при опоздании.

Для stereo признаки объединять по энергиям, а gain применять общий. Sidechain
только запрещает кандидаты и не звучит в выходе. Проверить одновременный реальный
удар снейра и бочки: veto не должен незаметно превращаться в безусловное подавление
всех совместных ударов; режим, окно совпадения и чувствительность должны быть явными.

### Закон усиления и измерение результата

База: `gain_dB = (target_dB - measured_dB) * strength_direction * ghost_weight`,
затем ограничения `[-max_cut_dB, +max_boost_dB]` и политика плотных пассажей.
Коэффициент амплитуды — `10^(gain_dB/20)`. Нулевую энергию обрабатывать через
явный floor; энергия переводится в dB через `10*log10`, амплитуда — `20*log10`.

Адаптивная цель использует прошлые уверенные удары в окне, заданном в секундах.
Задать ограниченную ёмкость, прогрев (до достаточной статистики — unity), поведение
после тишины/reset и исключение отвергнутых событий. Гост-зона имеет непрерывный
вес 0…1. Weighted-режим фильтрует только ветку измерения, не выходное аудио;
частотную характеристику выбрать на сравнении с RMS/peak и зафиксировать версию.

До/после измеряется одним методом по согласованным окнам реального входа и выхода
с учётом latency и Dry/Wet. Не подменять результат `measured + requested gain`.
Показатель разброса — стандартное отклонение уровней в dB по одному набору последних
N завершённых ударов; показывать N и состояние «недостаточно данных».

## Порядок реализации

Каждый пункт — отдельный обозримый PR. Галочка означает выполненные критерии,
а не начало работы. Порядок зависимостей: 01 → 02 → 03 → 04 → 05 → 06 → 07 →
08 → 09 → 10. Исследование 1.1 не задерживает этот путь.

### [x] PR 01 — Каркас и измерительный стенд

C++20, CMake presets Debug/Release, Ninja, Catch2, независимая DSP-цель;
Makefile как тонкая обёртка. Зафиксировать версии JUCE/Catch2 с учётом основного
проекта. Добавить генератор ударов с известными onset/уровнями и файловый runner
с настраиваемым разбиением на блоки. Версию хранить в `VERSION`, начать changelog.

**Готово:** чистый checkout конфигурируется, passthrough проходит тест,
runner даёт воспроизводимый отчёт; в README стоят проверенные команды.
Скачанные зависимости и аудиофайлы не попадают в git.

Реализовано: `beat_leveler_dsp` с passthrough, CMake presets и Makefile,
Catch2, генератор четырёх ударов, WAV runner с шаблоном размеров блоков и CSV
по повторно прочитанному выходу. JUCE 8.0.15 / Catch2 v3.8.1 закреплены;
ядро собирается без них. Это ещё не детектор и не левелер.

### [x] PR 02 — Контракт событий и доказательство latency

Аудит повторного использования детектора; минимальный потоковый интерфейс
prepare/reset/process, предвыделенные буферы, delay line и события с timestamp.
С временными известными onset/gain проверить планирование до атаки. Записать
решение о latency, поддерживаемых W/L, максимальных ёмкостях и переполнении.

**Готово:** импульс выходит ровно через заявленную L; смена разбиения на блоки
не меняет позиции. Есть тест границы дедлайна и late-event fallback. Зафиксирована
схема переноса общего DSP без зависимости сборки от соседнего каталога.

Реализовано: `OnsetEvent` с epoch, provenance и отдельным временем готовности,
`LatencyBudget` с округлением полного бюджета и кольцевой `DelayLine` для mono/stereo.
Тесты покрывают задержку 0 и ненулевую, in-place обработку, reset, границы бюджета,
стерео и произвольное разбиение host-блоков. Низкоуровневый fallback пока unity:
опоздавшее решение не меняет уже начавшийся удар; scheduler появится в PR 04.

### [ ] PR 03 — Детекция и уровни на файлах

Спектральный поток, причинный адаптивный медианный порог, НЧ-ветка, ограниченный
refractory interval. Peak/RMS/weighted измерение с доступом к истории онсета.
Спектральный профиль обучается по уверенным событиям в потоке, с явным прогревом.
Отдельный набор для настройки и замороженный контрольный набор реальных записей.

**Готово:** отчёт precision/recall, ошибки времени и уровней отдельно по бочке,
снейру, томам, гостам, флэмам и просачиванию. Проверено сохранение истории между
блоками. Выбран weighted-фильтр или записано, какой эксперимент ещё блокирует его.
Численные пороги качества реального детектора фиксируются по baseline до PR 04.

### [ ] PR 04 — Базовый gain и переходы

Фиксированная цель, strength, пределы подъёма/ослабления, плато и переход в
доступном минимуме. Политика плотных пассажей, непрерывный gain, анализ перегрузки.
Сначала проверить известные события, затем тот же тракт с реальным детектором.

**Готово:** на изолированных синтетических ударах без срабатывания ограничений
ошибка закона gain ≤ 0.1 dB при strength 0/0.5/1. Плато сохраняет нормированную
форму сигнала с численной погрешностью. Тест переходов отличает ступеньку gain
от естественной атаки; прослушаны паузы, хвосты и раскаты.

### [ ] PR 05 — Музыкальное поведение

Адаптивная цель, раздельная strength, прогрев, гост-зона, окно применения и
возврат к единице. Измерить влияние длины окна на хвост и просачивание.

**Готово:** синтетическое крещендо не сводится к одной фиксированной цели;
в защищённой зоне гостов воздействие стремится к нулю без скачка на границе.
Пределы соблюдаются, наложенные окна не суммируют подъём. На реальном материале
выбраны безопасные defaults и записаны случаи слышимого изменения хвоста.

### [ ] PR 06 — JUCE processor, VST3/AU и host contract

Mono/stereo main bus, optional sidechain, единый stereo gain, APVTS, стабильные
ID, версия схемы и сохранение настроек. Dry/Wet, difference, bypass с общей
задержкой. Reset при prepare/seek/loop, обработка пустых и меняющихся блоков.
Уникальные plugin/manufacturer IDs и bundle ID утвердить до первой внешней сборки.

**Готово:** VST3 загружается в Reaper, AU — в Logic; PDC совпадает с измеренной
задержкой. 0% wet и bypass дают задержанный dry, difference = wet − delayed dry.
Состояние восстанавливается; sidechain отключённый, пустой и активный проверены.
Offline bounce не теряет первые/последние события и не зависит от worker/UI.

### [ ] PR 07 — Интерфейс и достоверные метрики

Сила, авто/ручная цель, Dry/Wet; расширенные параметры по раскрытию. Ограниченная
история waveform, маркеры с confidence и пара измеренных уровней удара, gain,
индикатор разброса, прогрева и перегрузки. Отдельный источник телеметрии от DSP.

**Готово:** визуализация соответствует отчёту runner и выходному сигналу;
закрытие editor и перегрузка UI-очереди не меняют аудио. Проверены масштабирование,
автоматизация обычных параметров и восстановление настроек в host/Standalone.

### [ ] PR 08 — Пресеты и MIDI

Пресеты для бочки, снейра, томов, комнаты и перкуссии; оценить default strength
0.3–0.6 из идеи на прослушивании. MIDI: note/velocity mapping, note-off, timestamps
относительно задержанного аудио и отсутствие зависших нот после reset.

**Готово:** пресеты воспроизводимо загружаются; MIDI совпадает с аудиособытиями
в поддерживающих маршрутизацию хостах. Ограничения MIDI по формату/хосту записаны,
наличие API не выдаётся за работающую маршрутизацию. CLAP подключается отдельным
изменением только после проверки совместимости выбранного адаптера.

### [ ] PR 09 — Стабилизация и внешняя бета

Сборка/тесты в CI, валидаторы форматов, host-матрица, CPU/память, упаковка macOS,
подпись и notarization для внешней раздачи. Выбрать лицензию проекта и проверить
условия зафиксированных зависимостей перед распространением.

**Готово:** сохранены отчёты с версиями toolchain/OS/DAW и конфигурациями машины;
измерены максимум времени callback и запас до дедлайна под нагрузкой, память
не растёт после prepare. Внешняя сборка устанавливается на чистой целевой машине.
Инструкция описывает routing, PDC, ограничения, сброс и диагностику.

### [ ] PR 10 — Бета и 1.0

Несколько инженеров проверяют свои записи: close mics, плохая изоляция, тихая игра,
римшоты, флэмы, раскаты, смена громкости между частями. Собирать наблюдения и
численные результаты; реальные записи остаются вне git.

**Готово:** нет известных блокирующих дефектов звука/PDC/state; замороженный набор
проходит утверждённые пороги, прослушивание подтверждает пригодность defaults.
Опубликованы ограничения, changelog и воспроизводимая сборочная инструкция.
Релизные действия выполняются в рамках отдельной задачи на выпуск.

| Timing | Impulse PDC, dry/wet null при unity, difference null при unity, bypass, изменение latency, MIDI и offline bounce |
| Реальное качество | Отдельные precision/recall, ложные подъёмы, ошибка уровня, разброс до/после и прослушивание с согласованной громкостью по каждой записи |
| Realtime / state | Нет выделений/освобождений и блокировок в callback; измеренный CPU-бюджет; переполнение очередей, UI закрыт, автоматизация, сохранение/восстановление |

Реальные файлы берутся из `BEAT_LEVELER_REAL_KIT_DIR`. Без него соответствующий
прогон помечается skipped; релизный этап требует реального прогона. В отчёте
указывать версию детектора, параметры, набор и метод сопоставления событий.

## 1.1 — Связывание микрофонов

Один leader публикует события усиления для followers. Применяются общий gain,
одинаковые переходы и согласованная latency группы. Задержка «один блок» из идеи
не считается готовым решением: размер блока и порядок вызовов не задают надёжную
общую временную шкалу, а инстансы могут оказаться в разных процессах.

Сначала отдельный прототип Reaper/Logic/Live: timestamp/epoch, порядок callbacks,
parallel rendering и offline bounce, максимальное запаздывание доставки. Определить
поддержку разных процессов, распределение latency и reset группы. Затем выбрать
транспорт, обработку потери leader, overflow и устаревших событий. Не предполагать,
что одна SPSC-очередь допускает несколько читателей без отдельной схемы доставки.

**Выход этапа:** равные gain-кривые на связанных микрофонах, сохранение их
относительного времени и баланса; удаление/отключение leader не даёт зависания
или скачка. Неподдерживаемая конфигурация имеет явный статус и безопасное поведение.

| Музыкальные режимы: PR 05 | 2 недели |

До 1.0 получается 13–15 недель по исходным оценкам, без обещания календарного
срока при неполной занятости. После PR 02 переоценить DSP, после PR 06 — хосты.
CLAP, Windows и исследования не должны незаметно попадать в эту оценку.

Решения по сроку: latency и общий DSP — PR 02; weighted-мера и пороги качества —
PR 03; безопасные диапазоны и сохранение фразировки — PR 05; идентификаторы —
PR 06; лицензия и точная матрица поддержки — до внешней беты. Цена и итоговое
название остаются продуктовыми вопросами; исходные рыночные утверждения ещё
требуют отдельной проверки и не являются обоснованием технического плана.
