## Контекст и границы

Рабочее имя — **Beat Volumetric**. Репозиторий называется `beat-volumetric`.
Это левелер громкости отдельных ударов на одной
mono/stereo дорожке, связанный с основным проектом `../beat-equalizer`.

Исходная идея — `drum-leveler-project.md`. Исполнимый план, технические уточнения
и границы релиза — `docs/plan.md`. Не переносить сюда весь продуктовый документ.
Расхождения с исходной идеей явно описывать в плане, а не скрывать в реализации.

Основной репозиторий — источник совместимых решений; изменения в нём требуют
отдельной задачи. Не подключать его через абсолютный путь и не копировать целиком.
Его правила многоканального фазового выравнивания не являются правилами левелера.

В 1.0 нет ARA, редактора ударов, замены сэмплами, фазового выравнивания,
нейросетей и межинстансного связывания. Контракт будущего связывания предусмотрен
в модели событий, но не требует реализации транспорта до 1.1.

## Архитектура и C++

- C++20, без GNU-расширений; JUCE в адаптере плагина и интерфейсе.
- `src/dsp/` — потоковое ядро; не зависит от UI, `AudioProcessor` и модели редактора.
  FFT допускается через небольшой адаптер с заранее выделенной памятью.
- `src/plugin/` — JUCE processor, шины, параметры, состояние, editor.
- `tests/` — автономные DSP-тесты; `tools/` — файловый стенд и отчёты.
  `src/plugin/` появится на этапе JUCE-адаптера, сейчас плагин ещё не реализован.
- Детектор, измеритель, закон усиления и планировщик переходов — отдельные блоки.
  Событие содержит время во входном потоке; время готовности решения хранится отдельно.
- Совместимый стиль основного проекта: Allman, 4 пробела, `#pragma once`,
  без `using namespace juce` в заголовках. Локальное DSP-пространство имён —
  `beat::leveler`; общий код детекции сохраняет согласованный контракт.
- Зависимости фиксировать по версии/commit в CMake, не добавлять скачанные SDK в git.
- ID параметров и схема состояния стабильны после первой внешней сборки.
  Миграция состояния сопровождается тестом; новые ID не переиспользуют старые.

## DSP-инварианты

1. Аудиопоток не выделяет и не освобождает память, не берёт mutex, не делает I/O,
   не логирует и не ждёт worker/UI. Буферы и ограниченные очереди готовятся заранее.
   Потоковые FFT и статистика допустимы только с ограниченной стоимостью и профилем
   на минимальном блоке. Не переносить файловый `OnsetAnalysis::run` в callback.
2. Решение об усилении готово до выхода защищаемой атаки из delay line.
   Бюджет включает подтверждение онсета, окно измерения и переход до атаки.
   Нельзя прочитать уже отданные хосту сэмплы или скрыть дополнительную задержку.
3. Wet, dry, difference и внутренний bypass используют одну временную базу и
   согласованную latency. Изменение latency проходит согласованный с хостом путь.
4. Один скалярный gain на оба канала stereo. Анализ stereo не должен терять
   противофазный удар при суммировании L+R. Sidechain не подмешивается в выход.
5. На защищённом участке удара gain постоянен. Переходы и возврат к единице —
   явные исключения; не обещать неизменность всей огибающей при оконном gain.
6. Переходы между коэффициентами непрерывны. Кроссфейд двух синхронных копий
   эквивалентен изменению gain: он сам по себе не устраняет модуляцию хвоста.
7. Нет нелинейного клиппера или лимитера «для безопасности». Есть пределы gain
   и индикация перегрузки; нулевой вход не превращается в NaN/Inf или шум.
8. Пороги/окна задаются в dB, ms, Hz и секундах. Позиции событий — целочисленные
   64-битные отсчёты входного потока с явным reset/epoch при разрыве транспорта.
9. Результат не зависит от разбиения на host-блоки при одинаковой временной
   последовательности параметров. Пауза, seek, loop и повторный prepare не
   переносят старые события на новую временную шкалу.
10. Ложное срабатывание может поднять просачивание. Precision, recall и долю
    ложных подъёмов показывать отдельно; не прятать их в один средний балл.
11. UI получает ограниченную телеметрию без ожидания со стороны DSP. Переполнение
    UI-очереди может отбросить визуальные точки, но не менять звук.

## Работа и проверка

Один шаг плана — одна обозримая задача/PR. Использовать ветки `feat/`, `fix/`,
`docs/`, `test/`, `chore/`; интеграционная ветка до 1.0 — `main`, без `develop`.
После начального оформления работа идёт через PR и squash. Не выполнять
commit/push автоматически только ради закрытия сессии.

Команды сборки — в README: `rtk proxy make debug`, `rtk proxy make test`,
`rtk proxy make bench`. Чистое DSP-ядро собирается без JUCE; файловый стенд
подключает только его аудио/файловые модули. Проверять документацию, ссылки и diff.
Для DSP-изменения необходим тест известного дефекта или проверяемого свойства,
для UI — визуальная проверка, для шин/latency — проверка в целевом хосте.

Реальные записи не коммитить. Путь к стенду задаётся `BEAT_LEVELER_REAL_KIT_DIR`;
без него тесты реального материала явно пропускаются. В git — генераторы синтетики,
метаданные и численные отчёты без аудио. Пропуск реального стенда не означает
успешную проверку релизного качества.

Задача завершена, когда изменённое поведение проверено, план и README актуальны,
а `docs/status.md` содержит фактическое состояние и следующий шаг. Не отмечать
этап выполненным по одному наличию заглушки. Долгосрочные решения записывать в
`docs/decisions/` по мере появления; не плодить пустые шаблоны заранее.
